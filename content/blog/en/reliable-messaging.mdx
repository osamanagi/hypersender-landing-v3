Good messaging starts with a simple promise: the right person receives the right message at the right time. Keeping that promise means thinking beyond the send button.

This sample guide demonstrates the blog’s Markdown features while introducing a few useful engineering habits. Adapt the examples to your own application and messaging provider.

## Start with the message lifecycle

Treat a message as a small workflow with explicit states. A request being accepted is different from a message being delivered.

| State | What it means | What to show |
| :--- | :--- | :--- |
| Queued | Your application has saved the work | Waiting to send |
| Submitted | The provider accepted the request | Sent to provider |
| Delivered | A delivery receipt is available | Delivered |
| Failed | The attempt could not complete | Action needed |

> Make uncertainty visible. If you do not have a delivery receipt, describe the message as submitted rather than delivered.

### Keep a stable identifier

Give each logical message an identifier before sending it. Preserve that identifier when retrying so your application can detect duplicates.

```ts title="message.ts" {2,3}
type MessageJob = {
  id: string;
  idempotencyKey: string;
  recipient: string;
  body: string;
  attempts: number;
};

const job: MessageJob = {
  id: "message_001",
  idempotencyKey: "order_123:confirmation",
  recipient: "recipient-placeholder",
  body: "Your order is confirmed.",
  attempts: 0,
};
```

The `idempotencyKey` above is an application-level example. Check your provider’s documentation before sending it as an API parameter.

## Retry deliberately

Retries can help with temporary failures, but they can also create duplicate messages. Record every attempt and choose a bounded policy.

1. Classify the failure as temporary or permanent.
2. Retry temporary failures with increasing delays.
3. Stop after a defined number of attempts.
4. Expose the final outcome to the person managing the workflow.

```js title="retry-delay.js"
function retryDelay(attempt) {
  const base = 1000;
  const maximum = 30_000;
  const jitter = Math.random() * 500;
  return Math.min(base * 2 ** attempt + jitter, maximum);
}
```

This is a delay calculation, not a complete retry worker. Your worker also needs persistence, cancellation, and duplicate protection.[^retries]

## Give operators a clear view

A useful dashboard connects the message, its attempts, and its latest known status. Keep the most common tasks easy to find.

Before shipping, review this checklist:

- [x] Store a stable message identifier.
- [x] Distinguish submission from delivery.
- [ ] Add a bounded retry policy.
- [ ] Review delivery receipts and failure handling.

## Build on a small foundation

Start with **clear states**, *useful logs*, and a predictable retry policy. Add complexity only when the workflow needs it. ~~Retry everything forever~~ is rarely a useful operating model.
