تبدأ المراسلة الجيدة بوعد بسيط: تصل الرسالة الصحيحة إلى الشخص الصحيح في الوقت المناسب. ولتحقيق ذلك، نحتاج إلى التفكير فيما يحدث بعد الضغط على زر الإرسال.

يوضح هذا المقال التجريبي ميزات Markdown في المدونة وبعض المبادئ الهندسية المفيدة. عدّل الأمثلة لتناسب تطبيقك ومزوّد المراسلة الذي تستخدمه.

## ابدأ بدورة حياة الرسالة

تعامل مع الرسالة كسير عمل له حالات واضحة. قبول الطلب يختلف عن تسليم الرسالة إلى المستلم.

| الحالة | المعنى | ما يظهر للمستخدم |
| :--- | :--- | :--- |
| في الانتظار | حفظ التطبيق مهمة الإرسال | بانتظار الإرسال |
| تم التقديم | قبل المزوّد الطلب | أُرسلت إلى المزوّد |
| تم التسليم | وصل إشعار بالتسليم | تم التسليم |
| فشلت | لم تكتمل المحاولة | تحتاج إلى مراجعة |

> اجعل عدم اليقين واضحًا. إذا لم يصلك إشعار بالتسليم، فلا تعرض الرسالة على أنها سُلّمت.

### استخدم معرّفًا ثابتًا

امنح كل رسالة معرّفًا قبل إرسالها، واحتفظ به عند إعادة المحاولة حتى يتمكن تطبيقك من اكتشاف التكرار.

```ts title="message.ts" {2,3}
type MessageJob = {
  id: string;
  idempotencyKey: string;
  recipient: string;
  body: string;
  attempts: number;
};

const job: MessageJob = {
  id: "message_001",
  idempotencyKey: "order_123:confirmation",
  recipient: "recipient-placeholder",
  body: "Your order is confirmed.",
  attempts: 0,
};
```

الحقل `idempotencyKey` هنا مثال على مستوى التطبيق. راجع توثيق المزوّد قبل استخدامه كمعامل في واجهة API.

## أعد المحاولة وفق سياسة واضحة

قد تساعد إعادة المحاولة مع الأخطاء المؤقتة، لكنها قد تؤدي أيضًا إلى إرسال رسائل مكررة. سجّل كل محاولة وحدّد عددًا أقصى للمحاولات.

1. ميّز بين الأخطاء المؤقتة والدائمة.
2. زِد فترة الانتظار بين المحاولات.
3. توقّف بعد عدد محدّد من المحاولات.
4. اعرض النتيجة النهائية للشخص المسؤول عن سير العمل.

```js title="retry-delay.js"
function retryDelay(attempt) {
  const base = 1000;
  const maximum = 30_000;
  const jitter = Math.random() * 500;
  return Math.min(base * 2 ** attempt + jitter, maximum);
}
```

هذا المثال يحسب مدة الانتظار فقط. تحتاج خدمة التنفيذ أيضًا إلى حفظ المهام ودعم الإلغاء ومنع التكرار.[^retries]

## ابنِ أساسًا صغيرًا

ابدأ **بحالات واضحة** و*سجلات مفيدة* وسياسة يمكن توقعها. ~~إعادة المحاولة بلا نهاية~~ ليست عادةً طريقة تشغيل مفيدة.

للتفاصيل الخاصة بالمزوّد، راجع [توثيق هايبرسندر](https://docs.hypersender.com).

[^retries]: يجب أن تتوافق سياسة إعادة المحاولة مع أنواع الأخطاء والحدود الواردة في توثيق مزوّد المراسلة.
